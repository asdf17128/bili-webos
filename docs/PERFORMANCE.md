# 性能:观测与优化

**规矩:先能测,再优化。** 这里每一条改动后面都跟着"改前 vs 改后"的数字;
测不出改善的改动不留。

## 一、观测

| 工具 | 用途 |
|---|---|
| `app/src/utils/perf.js` | app 内的轻量打点(定长环形数组 200 条,不随时间增长) |
| `tools/perf.mjs` | **真机**驱动 + 报告(CDP over SSH) |
| `tools/perf-sim.mjs` | 降速模拟器(默认 CPU 6×)+ **A/B 对照** |
| `app/src/utils/perfFlags.js` | 优化开关,用于 A/B;并提供**预取闸门** |

覆盖的交互环节:跟手(按键→焦点画出)· 翻页 · 图片 · 页面切换 · 播放器首帧
(拆 5 段)· 评论竖栏。每次都同时报**长任务**和**内存**。

三条约束:
1. 打点本身不能成为负担 —— 一次 `performance.now()` + 一次写入,不做字符串拼接。
2. 不依赖新 API —— 用户机器上有 Chromium 68/79(owner 的 C4 是 120)。
   `longtask` 拿不到就如实标注"该机型无法观测",不假装有数据。
3. 耗时和内存一起看 —— 否则优化会滑向"缓存一切",在 deviceMemory=2GB 的
   电视上那是拿内存换卡顿。

### 踩过的测量坑(比结论更值钱)

- **用 git stash 做对照会把打点一起收走**,对照那栏全是"无样本"。
  → 优化必须放在**运行时开关**后面,同一构建、同一打点,只翻开关。
- **n=1 的结论没有意义**:首帧被一次重试带偏成 12.7s。→ 改成多次取中位数。
- **多次打开播放器测不出引擎 import 成本**:只有第一次付钱,后面走模块缓存。
  → 每轮 reload 页面,只测"冷启动后的第一次"。
- **模拟器测不出懒加载延迟**:桌面 Chrome 一次性把整屏图都加载了。
  → 图片相关的结论必须在真机上复核。

## 三、优化与实测效果(6× 降速模拟器 A/B,同构建只翻开关)

| 指标 | 关优化 | 开(无闸门) | **开 + 闸门** |
|---|---|---|---|
| 翻页 | 279ms | 36ms | **31ms** |
| 图片 p50 | 285ms | 575ms ❌ | **266ms** |
| 播放器首帧 | 1850ms | 4185ms ❌ | **1700ms** |
| 长任务合计 | 310ms | 3041ms ❌ | **382ms** |
| 内存 | 14MB | 14MB | 14MB |

**最重要的一条教训在中间那列**:无节制预取会把机器拖垮 —— 翻页是快了,
但图片慢一倍、首帧慢 2.3 倍、长任务涨 10 倍。观测把这个错误挡在了发版前。

### 预取闸门(`perfFlags.js`)

预取是"闲时才做的事":
- 播放器开着 → 全停(它是前台重活)
- 同一时刻只允许**一个**预取在飞,不排队堆积
- 缩略图只预取**下一行**(两行会抢当前可见图片的带宽)

### 播放引擎预热(冷启动后第一次打开,每轮 reload,n=3)

| | 首帧中位 | 引擎 import | 内存 |
|---|---|---|---|
| 预热开 | **1417ms** | 5ms | 19–20MB |
| 预热关 | 1884ms | 271ms | 15–19MB |

首帧 **−467ms(−25%)**。多占的几 MB 是用户迟早要付的钱,只是挪到了空闲时段;
且要求停留 2 秒后才预热 —— 免得为"开机即退出"的人白花内存。

## 四、测过但**没有效果**的改动

- **滚动脱离 React**(焦点移动不再触发两次全量重渲染):对照实验中差异只有
  1–2ms,在噪声里。真机 p95 92ms 的尾巴**不是** React 渲染造成的 ——
  当前假设是图片解码抢主线程,待真机验证。改动保留(方向正确、无副作用),
  但**不作为已验证的收益**。

## 五、真机最终结果(LG C4,2026-08-31,同一时段交替 A/B ×3 轮)

用 `FLAGS` 开关在**同一构建**上交替跑 OFF/ON,消除跨天网络漂移:

| 指标 | 优化前 | 优化后 | 改善 |
|---|---|---|---|
| **翻页 p50** | 387ms | **74ms** | **−81%** |
| **图片 p50** | 1427ms | **462ms** | **−68%** |
| 图片 p95 | 1775ms | **997ms** | −44% |
| **长任务合计** | 1716ms | **864ms** | **−50%** |
| 跟手 p50 | 29.0ms | 27.5ms | −5% |
| 跟手 p95 | 84.3ms | 77.0ms | −9% |
| 内存 | 10MB | 10MB | 持平 |

翻页 4 次**全部命中预取**(优化前 0 次)。

### 中途发现的两个问题(都靠观测抓到)

1. **无节制预取会拖垮机器**:第一版让图片慢一倍、首帧慢 2.3 倍、长任务涨 10 倍。
   → 加预取闸门(播放器开着全停、同时只允许一个在飞、缩略图只预一行)。
2. **预取抢按键路径**:跟手 p50 从 24.5 退到 30.2ms。
   → 预取一律**等焦点停稳 200–250ms** 再做。连续按方向键时零额外工作。

### 观测工具自己的 bug

一个 200 条的大环形数组,被一屏 173 张图片的打点挤爆,翻页记录全丢,报告显示
"无样本"。→ 改成**按指标分桶**(每桶 60 条),互不挤占。

## 六、第二轮:再挖 25 个点(2026-08-31)

### 6.1 修正了一个测错的指标

原来的"图片"量的是**卡片挂载 → 图片出现**。但卡片是一次性全挂载的,深处的行
挂载后要等用户滚到才加载,那段等待被算进了指标 —— 数字被撑大好几倍,还掩盖了
真实问题。改成量**决定加载 → 图片出现**(用户真正盯着灰块的时间)。

### 6.2 真机最终数字(新指标,冷缓存)

| 指标 | 优化全关 | 优化全开 | 改善 |
|---|---|---|---|
| **图片 p50** | 1467ms | **210–250ms** | **−85%** |
| **图片 p95** | 1961ms | **470–560ms** | **−73%** |
| **翻页 p50** | 415ms | **73–80ms** | **−81%** |
| 跟手 p95 | 124ms | 79–88ms | −32% |
| 跟手 p50 | 24ms | 28ms | 见 6.4 |

### 6.3 这一轮真正起作用的:代理透传缓存头

代理原来把上游的 `cache-control`/`etag`/`last-modified` **全丢了**,浏览器于是
一次都不缓存 —— 往回滚要重下,**预取下来的图真正显示时再下一遍**(等于预取白做)。
透传之后拿到 `max-age=31536000`。

### 6.4 当时的跟手测试未测出明确收益

当时双 rAF 空操作基线为 **p50 33ms**，跟手记录为 24–30ms。两者受帧调度影响，
不能直接相减得出真实渲染成本，也不能据此断言已无优化空间。该轮 OFF/ON 差异很小，
没有测出明确收益；DOM 焦点更新与最终屏幕绘制需要区分。

### 6.5 当时的 CPU 采样

真机滚动 7.5 秒的采样:主线程 **66% 空闲**,我们的 JS 只占 ~250ms,
引擎内部(布局/绘制/解码)占 2169ms。该样本提示优先检查布局、绘制与图片解码，
不能推广为所有页面或旧型号电视的 JS 都没有性能问题。

### 6.6 试过但没有效果、已回退的

| 改动 | 结果 |
|---|---|
| 缩略图 420w → 336w | p50 457 vs 458,无差别(瓶颈不是字节数) |
| 缩略图预取 1 行 → 2 行 | 358.7 vs 360.1,无差别 |
| 离屏卸载图片 | 反而更慢(p50 454→492) |
| 翻页分批渲染 | 78.6 vs 73,无改善 |
| 滚动脱离 React | 1–2ms,噪声内(与 6.5 一致:JS 不是瓶颈) |

### 6.7 还剩什么

- **翻页 73ms**：该口径包含帧调度，不能减去另一个基线就算出渲染耗时。虚拟化
  会影响滚动几何，需先证明长列表上的瓶颈与收益，再决定是否实施。
- **图片 p50 ~220ms**:基本是 CDN 往返延迟。再快只能靠更激进的预取,
  而那会重新引入"抢带宽"的老问题。
- 这些数字是 2026-08-31 的 C4 场景结果。不能代表所有机型、网络或列表长度，
  后续版本仍需用一致口径重新测量。

使用 `tools/perf-external.mjs`，4 列设置，每轮 32 个实际焦点变更样本：

## 八、稳定性候选 4 的已完成观察（2026-10-13，未发布）

同一 LG C4 / Chromium 120，安装 `2.3.0 stability-test.4`。同一 document 内完成
3 次热身、20 次 4K HEVC 播放/暂停/退出及 5 次加载中退出，**145 条清理与行为断言
通过**。第 0/5/10/15/20 轮统一强制 GC 后保留堆分别为 **5,708,112 / 5,800,312 /
5,852,092 / 5,877,828 / 5,918,456 B**，累计增加 **210,344 B（3.69%）**，来源尚未
归因，保留 **NEEDS_REVIEW**；清理断言通过不等于无泄漏。五点 DOM 均为 **608**、
监听器 **210**、document **1**；这些指标不含 GPU 或全进程内存。

循环前后各 **32 次实际焦点变化**，p50 **3.2→3.5ms**、p95 **4.2→6.0ms**，
在既定预算内。两次采样没有重载页面，测量仍是 keydown→DOM 焦点变更，
不含物理遥控链路或最终绘制。见[同页循环证据与判定](ux-evidence/2026-10-13-stability/final-tv-4/lifecycle/README.md)。

直播完成 15 分钟、16 个样本，持续交付 **833 条聊天 / 2,857 个互动事件**；relay
累计连接 3 次，心跳超时后自主恢复交付，退出清理通过。原生 HLS 视频重连 1 次，
最大进度间隔 **13.326 秒**，同期上游出现响应中止与响应头超时，流畅性仍为
**NEEDS_REVIEW**，尚不能确定 CDN 与中间网络各自的影响。原生帧计数全部为 0，
视为不可测，不能宣称零丢帧。GitHub 更新源最后两轮失败使本段工具 **43/45、exit 1**；
后续成功探针不覆盖原失败。见[直播观察与限制](ux-evidence/2026-10-13-stability/final-tv-4/live/README.md)。

**60 分钟 4K50 长播已完成并通过。** 15:51:11.895 开始，16:51:14.826 完成清理（Asia/Shanghai），有效采样经过 3,602,102ms；61 轮样本与清理合计 67/67 条断言。所有样本为 3840×2160、HEVC、50fps 元数据，登录/VIP 有效；一次自然循环，新增解码 180,118 帧、新增 dropped 0，最大进度采样间隔 1.999s，无 >3s 调查项。主站/直播/更新源各 61/61 成功，服务 uptime 增加 3600 秒，无页面或服务重启证据。

自然 CDP JS 堆为 **6,142,540–7,983,200 B**，首尾 6,142,540→7,439,312 B，期间多次回落；不将其当作强制 GC 后保留量，也不取消上述同页循环的内存 finding。主线程长任务 **3 次，总 172ms，最长 60ms**，包含采样期间开销。日志快照观察到 9 条直播 API 连接重置重试，逻辑请求全部自动恢复；不是底层零故障。完整分钟数据、分段解码及采样限制见 [60 分钟证据](ux-evidence/2026-10-13-stability/final-tv-4/soak/README.md)。
