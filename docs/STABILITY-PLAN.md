# 稳定性测试方案

本方案针对当前播放修复候选包，目标是发现长期播放、反复切换和网络故障后的资源与状态问题。执行范围是本地完整回归、真实服务故障压力、LG C4 真机长播及交互耐久；**测试完成不等于授权发布**。正式结果、失败样本和未验证范围必须另存到本次证据目录，不以本方案中的目标充当结果。

本轮证据目录：[`ux-evidence/2026-10-13-stability/`](ux-evidence/2026-10-13-stability/)。相关历史基线见 [PERFORMANCE.md](PERFORMANCE.md)，功能用例注册表见 [TESTCASES.md](TESTCASES.md)，海外复测见 [NETWORK-TESTING.md](NETWORK-TESTING.md)。

## 1. 范围与环境

| 环境 | 本轮验证内容 | 不代表什么 |
| --- | --- | --- |
| 确定性浏览器 + HTTP 夹具 | 遥控交互、加载失败、重试预算、退出清理、签名备用地址、会话隔离 | 不证明电视硬件解码或报告者当地网络可用 |
| 实际生产服务 + 本机 HTTP socket | 超时、连接重置、排队、取消、并发、错误后的可用性和资源回收 | 不用压测 B 站公网，不声称复现了家庭路由器故障 |
| 真实 Node 0.12.2 / 8.17.0 | 老设备服务运行时、ES5 语法及关键请求通路 | 不等于 C6/C9 的硬件、Chromium、内存验收 |
| LG C4 / 已安装生产构建 | 会员 4K 解码、60 分钟长播、同页重复进出、直播、错误恢复 | 单机样本不能推广到全部电视，也不能证明长期永不泄漏 |

开始前记录 Git commit、工作树差异、测试构建标记、IPK SHA256、安装的前端 bundle SHA256、电视型号/浏览器/服务 Node、时区和起止时间。账号仅记录登录及会员有效布尔值；以 `nav` 实际响应核对，不以残留 Cookie 判断。确认电视独占，避免另一个脚本改变同一台电视的播放状态。

保存偏好原值，结束逐项核对恢复。不开关路由器、不修改家庭 DNS、不改关注/收藏/稍后再看等账号列表、不退出真实账号。正常播放可能产生观看历史。CDP 截图仅验 UI；没有系统视频平面截图权限时，不绕过权限，也不将黑色 GPU 截图认定为播放失败。

## 2. 风险矩阵与必须完成的层次

| 编号 | 风险 / 触发条件 | 方法与最小规模 | 通过判据 |
| --- | --- | --- | --- |
| S-01 | 修复破坏旧功能或旧运行时 | 完整本地门禁一次；必要修改后重跑受影响层，最终冻结源码后完整一次 | 必需项全过；缺 Docker/Python 等只能记未验证，不能记通过 |
| S-02 | 约 20 分钟后全部请求失败 | 4K50 连续 60 分钟，不重启服务、不刷新页面；每分钟并行探测主站、直播、更新源 | 61 轮有效样本；实际媒体持续前进；主站/直播每轮成功；服务 uptime 单调增加；第三方失败单独保留 |
| S-03 | 解码器、DOM、定时器或媒体连接随切换累积 | 同一 document 至少 20 次点播进入→真实解码→退出；第 0/5/10/15/20 轮采集资源 | 每轮退出后 video/播放器实例释放；没有退出后新发媒体请求；保留堆若持续增长须单列调查，即便未超预算；无页面刷新掩盖 |
| S-04 | 直播长看后断流、重复弹幕订阅或重连失控 | 当前在播房间连续 15 分钟；另测重复进入和退出；聊天停更 ≥120s 时独立取房间历史 | 播放及聊天持续交付，重连有期限和退避；房间仍有新聊天而 relay 停交付即失败；安静/无法确认房间记未验证；退出后订阅停止 |
| S-05 | 致命错误暂停媒体后永久黑屏 | 真机解码中分别注入致命网络/媒体错误和原生倍速错误；另用真实坏域名测试 CDN | 有可聚焦重试入口；按原 cid/位置恢复实际解码；轻微错误不重建；有限自动重试；退出后不重试 |
| S-06 | 上游故障耗尽连接池，之后所有请求阻塞 | 真实服务反复混合成功、重置、无响应、截断、取消与队列等待 | 每请求在期限内且恰好交付一次；POST/部分响应不重发；批次后健康请求成功；连接/队列回落 |
| S-07 | 画质切换、快进、自然片尾引发状态错乱 | 真机会员画质/编码回退、快进取消/提交、重复/停止/下一集专项 | 实际解码尺寸、时间推进和选中状态一致；快进取消不提交；片尾策略一致；无迟到事件覆盖新意图 |
| S-08 | 长会话操作越来越慢 | 同页循环前后相同设置/相同路径的焦点样本；长播 JS 堆/长任务/丢帧 | 使用相同口径比较；超过预算必须调查；不能用重载后的更快结果证明未泄漏 |
| S-09 | 失败报告不可用或泄露凭据 | 真实电视诊断 QR 解码 + 受控全失败诊断 | 成败均生成报告，错误有域名/类别/耗时；无 Cookie、用户身份、媒体完整签名 URL |

必要项以发现现有修复相关的稳定性缺口为目的。真实账号写入、电视断电/待机唤醒、24 小时长跑、多型号和海外现场测试不加入本轮通过数；第 8 节列出扩展条件。

## 3. 执行次序与命令

所有命令从仓库根目录运行，依赖以仓库现有安装为准。每次运行使用独立输出目录，保存退出码和完整日志，禁止覆盖首次失败。日志中如包含账号内容，先脱敏再纳入 Git。

### 3.1 本地层（可与真机长播并行）

```sh
bash tools/verify.sh --no-tv --ux
bash tools/verify.sh --sim --no-tv
```

第一条包括服务单测、媒体选择/杜比逻辑、ES5 与 ES2016、真实旧 Node、构建、遥控 UX、会话与端口、代理退出、播放器加载、弹幕、片尾、直播、CDN、诊断及家庭检测 HTTP 合约测试。第二条使用真实服务桥和浏览器网络通路；缺少真实账号的项目应明确跳过。两条须顺序执行，避免争用 Vite 或服务端口；浏览器套件运行中不改应用源文件，防止 HMR 改变生命周期。

```sh
STABILITY_ROUNDS=50 STABILITY_OUTPUT=/tmp/bili-stability/service \
  node tools/test-service-stability.mjs
```

真实服务压力使用隔离状态目录，测试流量只进入本机夹具。默认每种故障 50 次，故障请求后再发健康请求：一次/二次连接重置、POST 不重放、HTTP 503、截断、响应头/体停滞、gzip 正常/损坏、DNS 超时/取消及重试取消；另测 50 轮连接池满载，每轮 2 个占用、12 个排队超时、6 个取消及随后恢复。生产 `service.js` 另有四类代理失败/取消，各 50 次及健康恢复。以实际脚本结果核对完成数，不把计划次数写成已完成数。

故障夹具使用 120ms 期限加速覆盖，完整工具有 180s watchdog；它验证期限与清理机制，不意味着生产超时配置为 120ms。记录 ClientRequest 创建/close 计数、Agent active/queued/idle 和夹具 socket，最终销毁测试连接池后应归零；不只用 `Promise.all` 返回或笼统的活动句柄数宣布无泄漏。每批结果必须注明目标故障是否实际触发、客户端是否及时结束，以及随后的健康请求是否成功。

### 3.2 冻结和确认真机测试包

使用已验证候选包，核对安装 hash 与当前构建。电视所有步骤由一个执行者串行调度；本地构建可以并行，部署、重新启动、遥控和另一个 TV 测试不可以与长播并行。需要改产品代码时结束当前证据段，构建新包并重新开始受影响的耐久段；旧包的时间不能累加到新包。

不得在长播中运行不带 `--no-tv` 的 `verify.sh`：它会部署并重启 App。只读采样可以并行，但应记录额外观察流量。

### 3.3 60 分钟真实 4K50 长播

```sh
SOAK_MINUTES=60 SOAK_BVID=BV1sapi6qE72 \
  SOAK_MIN_WIDTH=3840 SOAK_MIN_HEIGHT=2160 SOAK_CODEC=hevc SOAK_MIN_FPS=50 \
  UX_OUTPUT=/tmp/bili-stability/soak-60m \
  node tools/test-network-soak-tv.mjs
```

使用同一 BVID、qn 120、循环模式，播放超过历史约 20 分钟故障窗口三倍。每分钟记录实际分辨率、编码、帧率元数据、解码/丢帧计数、缓冲、媒体时间、paused/readyState、服务 uptime、三类 API 状态/耗时，以及 CDP JS 堆、主线程长任务。帧率元数据不等于面板输出帧率。

每个稳定样本须核对 3840×2160 及目标编码；仅 `videoWidth > 0` 不足以给 4K 项判通过。自然循环须记录，不将时间回到 0 当作卡死；计数重置后按播放段计算丢帧，不能将末次累计值盲目相加。

现有工具每秒采样进度、以最大推进间隔 <15 秒作失活检测。这是严重停滞门禁，不是“15 秒以下都流畅”：所有 >3 秒间隔需检查对应缓冲/事件和采样延迟。一次采样的约 1 秒间隔包含定时调度，不能直接写成逐帧卡顿。

开始后不主动暂停、不 seek、不切画质、不重载。发生非致命失败仍保留余下时间线，观察其他通路及自恢复；如崩溃无法继续，保存错误、服务状态及已完成时长，不用补跑几分钟拼接成完整 60 分钟。

### 3.4 同一页面的资源回收与直播耐久

```sh
TV_CYCLES=20 UX_OUTPUT=/tmp/bili-stability/lifecycle \
  node tools/test-playback-lifecycle-tv.mjs
LIVE_MINUTES=15 UX_OUTPUT=/tmp/bili-stability/live \
  node tools/test-live-stability-tv.mjs
```

这两个入口属于本轮新增测试工具，须连同实际执行结果验收；不能只因脚本已写好就把对应项标为通过。

同页循环测试须单独保存唯一 document 标识，贯穿全部 20 轮。先完成若干热身循环，再使用同一视频、相同首页内容与同样等待时间比较空闲状态。退出必须通过应用正常 Back 路径；不能删 DOM 或直接清空测试状态代替产品清理。

每轮先确认媒体 readyState≥2、尺寸非零且时间实际推进，再退出并等待有上限的清理窗口。记录 video 数、播放器引用、媒体请求变化及 DOM 数；条件允许时记录前端事件监听器、Blob URL、后台连接/句柄及直播订阅。不可观测字段记为“不可测”，不得用 0 替代。

JS 堆同时保留自然走势和同口径的保留量。若使用 `HeapProfiler.collectGarbage`，明确标为**强制 GC 后保留量**，各检查点相同处理，不能据此推断自然 GC 峰值、总进程内存或 GPU 内存。堆只涨一次可能是缓存热身；连续增长须结合对象/连接来源解释，不能仅凭末值低于某个宽松上限判无泄漏。

媒体重连由既有 `__liveDiag` 安全计数：单次失败段 attempt≤12、connect≤13，无 gave-up；playing 后预算可重置，累计次数仍全部报告，不把它说成 socket 总量。工具结束恢复包装的 push/request，并独立移除自己的监听器/observer。

relay 使用服务新增的 `danmakuState` 记录相位、连接尝试次数、最近包/消息/交付/心跳时间和关闭码，错误只导出是否存在；不保存错误原文、聊天文本或 URL。这些是生产模块的诊断计数，**不是电视操作系统 socket 计数**。旧包没有该状态时保留不可测缺口；聊天 event/frame 数不能替代连接次数。短暂 connecting/authenticating/backoff 属于恢复过程，记录 `needs_review`，不直接当作永久失活。持续心跳也不能证明聊天仍在交付。

每分钟记录实际收到聊天的 `lastFrameAt`，非聊天事件另记。停帧 ≥120 秒才调用同房间 `gethistory` 独立对照：仅保存条数及时间，`timeline` 按北京时间 `+08:00` 解析，不依赖电视时区。历史最新聊天在上次交付 5 秒之后，且距探针时间为 −30 至 90 秒，可确认房间仍活跃；若设备/服务器时钟不一致，两次历史探针在同一停交付区间内继续推进也可确认。此时判 `active_room_relay_stale` 失败。历史空、老旧或请求失败只记 `quiet_or_unverified`/`unverified`；不误判安静房间，也不计为聊天通过。探针结束后重新采样交付，避免请求期间已恢复却仍误判。

媒体重试、播放推进间隔 ≥3 秒、relay 重连/暂未连接、长期缺少心跳回复或聊天连续性未确认，均保留 `needs_review`，即使硬门禁全部通过也不能返回全绿。报告分开 `gatesPassed`、`pass`、`status`，`needs_review` 和失败都退出非零；初始认证尚未完成的样本可以有人工解释，但不能静默删除。媒体间隔 ≥15 秒仍属于失活门禁。完整生产模块的重连/stop 取消以及工具自身判据和清理验证另行运行：

```sh
RELAY_STABILITY_OUTPUT=/tmp/bili-stability/live-relay-local node tools/test-live-relay-reconnect.mjs
LIVE_MONITOR_OUTPUT=/tmp/bili-stability/live-monitor-local node tools/test-live-stability-monitor.mjs
```

直播从当前真实列表选在播房间，记录 room id、选择原因、实际格式/画质和连续观察时长；安静房间无聊天不算弹幕成功。若房间只有一档，画质切换记跳过并尝试另一在播样本；仍不可获得则保留缺口。跨房间测试要核对旧订阅关闭，不能只看到新弹幕就判清理成功。

候选 3 的累计帧门禁曾漏过约十分钟无交付，独立历史对照确认失败；原结果不改写。新增连续性判据的本地 21 项与同判据复核见 [live-continuity-monitor](ux-evidence/2026-10-13-stability/live-continuity-monitor/README.md)。旧四次连接预算的本地通过只说明旧规则被执行，不证明其符合长看恢复需求；最终服务修复仍需同包完整真机耐久。

原始 JSON 必须含每轮数据和断言，不只保留汇总。若新增脚本发现无法观测某个指标，在最终执行矩阵中保留该缺口。

## 4. 预先约定的判据和报告口径

| 维度 | 门禁 / 处理原则 |
| --- | --- |
| 崩溃与失活 | 零未捕获致命异常、零意外 App/服务重启、零无法恢复的播放器冻结；出现即失败 |
| 60 分钟完整性 | 全程同一构建、同一 document、服务 uptime 增加；缺采样/工具断线须注明，不能充当完整覆盖 |
| B 站请求 | 主站及直播响应 HTTP 200 / code 0；失败保留，确认是否请求级恢复成功。不能用同期 GitHub 成败替代 |
| 第三方更新源 | 独立报成功数、失败数、超时和恢复；失败使“所有外网目标通过”不成立，不自动归类为播放失败 |
| 长播解码 | 目标 4K 实际尺寸贯穿样本，时间推进；本轮固定 C4/4K50 基线以零持续丢帧为目标。任何新增丢帧先保留时间段再判断，不能用首尾平均值隐藏集中卡顿 |
| 同页清理 | 每轮空闲后无 video/活动播放器，无退出后的持续媒体拉取或旧直播订阅交付；堆/DOM/连接的持续线性增长均需调查 |
| 内存趋势 | 自然 GC 峰谷与统一 GC 后保留量分开；后半段检查点连续增加且累计 >max(3 MiB, 热身保留量的 25%) 触发失败调查。此为本轮敏感告警预算，不是全机型内存限额；低于预算也不能冲抵已找到的泄漏 |
| 遥控响应 | 同一 document、相同内容/设置、至少 30 次实际焦点变化；p95 >50ms 或较前测增加 >max(10ms, 50%) 须调查。keydown→DOM 变更只代表 JS/DOM 响应，不含物理遥控链路/绘制 |
| 请求期限 | 故障请求必须按生产配置和显式调度容差结束、恰好一次结果；不得无界重试或剩余排队。压力后正常请求恢复，资源回到稳定区间 |
| 诊断 | 有效 QR 可从电视截图解码；失败有明确类别，报告无凭据/完整签名媒体 URL；失败不能生成“全绿”报告 |

告警预算在执行前约定，发现误报时先检查采样方法与环境，保留原判断及更正原因。不得为了已有结果通过而提高阈值。不能观测或未执行的门禁写 `NOT_RUN`/`UNVERIFIED`，不写 `PASS`。

## 5. 证据结构

本轮目录至少包含以下内容（最终文件名允许在汇总内映射）：

```text
2026-10-13-stability/
  environment.json       commit、设备/运行时、测试包及安装 hash、时间
  local/                 完整门禁日志、退出码、模拟结果
  service-stress/        各故障批次、请求/连接/资源指标与恢复结果
  soak-60m/              分钟时间线、原始错误、按域名统计和完整时长
  lifecycle/             同一 document 的逐轮资源与焦点数据
  live/                  连播、弹幕、换房/退出清理证据
  regression/            真机恢复、CDN、会员、快进、片尾与 smoke
  summary.json           每项 PASS/FAIL/SKIP/NOT_RUN、证据路径、限制
```

保存首次失败和修复后的完整重跑；有意义的图只保留 UI 与非个人数据。网络日志用目的 host、类别、状态、耗时、计数描述，不存完整媒体 query、Cookie、请求头、用户资料或私密内容。保留工具运行时间和采样缺口，使后来可以区分产品错误、上游失败和测试工具失败。

## 6. 失败处理

1. 先保存现场：最后正常时刻、错误时刻、媒体状态、各域名响应、后台 uptime 与脱敏错误。优先读日志，避免马上刷新抹掉证据。
2. 验证注入或探针实际生效。例如 CDN 请求确实打到坏域名、键确实到达、document 没偷偷重载；工具问题仍保存为失败尝试。
3. 将产品、上游/网络、环境和工具失败分开。外部故障不自动判产品有 bug，但用户仍需看到重试与恢复能力；不能把“网络问题”当作无限加载的理由。
4. 新修复先用同一条件让旧实现失败，再验证新实现。修改后重跑影响链，并在最终冻结版本上重跑完整本地门禁；长播路径的代码变更要重新计时耐久段。
5. 所有已证实用例追加到 `TESTCASES.md`；适合日常运行的确定性合约纳入 `verify.sh`，真实长跑保持显式独占执行，避免默认脚本意外接管电视。

## 7. 完成条件与发布门禁

本轮测试“完成”要求：风险矩阵各必要项有实际结果和原始证据；失败有分类及处理结论；所有测试注入已移除、偏好恢复、电视回首页；本地辅助服务由启动者清理。尚未解决或没有条件验证的内容须明确列出。

候选包达到“可考虑发布”至少要求本地必需门禁通过、包与设备身份一致、60 分钟播放/主站/直播稳定、同页资源清理和直播通过、恢复/CDN及必要功能回归通过、无未处置的崩溃/失活/泄漏。第三方源失败不得从报告删除，应说明更新检查是否给出有界失败且不阻塞使用。若需要接受残余风险，必须由维护者明确决定，不能由测试脚本将其静默跳过。

**本轮不执行发布、推送 release 或 Homebrew 更新。** 测试结论与发布授权是两个独立步骤。
