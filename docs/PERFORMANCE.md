# 性能:观测与优化

**规矩:先能测,再优化。** 这里每一条改动后面都跟着"改前 vs 改后"的数字;
测不出改善的改动不留。

## 一、观测

| 工具 | 用途 |
|---|---|
| `app/src/utils/perf.js` | app 内的轻量打点(定长环形数组 200 条,不随时间增长) |
| `tools/perf.mjs` | **真机**驱动 + 报告(CDP over SSH) |
| `tools/perf-sim.mjs` | 降速模拟器(默认 CPU 6×)+ **A/B 对照** |
| `app/src/utils/perfFlags.js` | 优化开关,用于 A/B;并提供**预取闸门** |

覆盖的交互环节:跟手(按键→焦点画出)· 翻页 · 图片 · 页面切换 · 播放器首帧
(拆 5 段)· 评论竖栏。每次都同时报**长任务**和**内存**。

三条约束:
1. 打点本身不能成为负担 —— 一次 `performance.now()` + 一次写入,不做字符串拼接。
2. 不依赖新 API —— 用户机器上有 Chromium 68/79(owner 的 C4 是 120)。
   `longtask` 拿不到就如实标注"该机型无法观测",不假装有数据。
3. 耗时和内存一起看 —— 否则优化会滑向"缓存一切",在 deviceMemory=2GB 的
   电视上那是拿内存换卡顿。

### 踩过的测量坑(比结论更值钱)

- **用 git stash 做对照会把打点一起收走**,对照那栏全是"无样本"。
  → 优化必须放在**运行时开关**后面,同一构建、同一打点,只翻开关。
- **n=1 的结论没有意义**:首帧被一次重试带偏成 12.7s。→ 改成多次取中位数。
- **多次打开播放器测不出引擎 import 成本**:只有第一次付钱,后面走模块缓存。
  → 每轮 reload 页面,只测"冷启动后的第一次"。
- **模拟器测不出懒加载延迟**:桌面 Chrome 一次性把整屏图都加载了。
  → 图片相关的结论必须在真机上复核。

## 三、优化与实测效果(6× 降速模拟器 A/B,同构建只翻开关)

| 指标 | 关优化 | 开(无闸门) | **开 + 闸门** |
|---|---|---|---|
| 翻页 | 279ms | 36ms | **31ms** |
| 图片 p50 | 285ms | 575ms ❌ | **266ms** |
| 播放器首帧 | 1850ms | 4185ms ❌ | **1700ms** |
| 长任务合计 | 310ms | 3041ms ❌ | **382ms** |
| 内存 | 14MB | 14MB | 14MB |

**最重要的一条教训在中间那列**:无节制预取会把机器拖垮 —— 翻页是快了,
但图片慢一倍、首帧慢 2.3 倍、长任务涨 10 倍。观测把这个错误挡在了发版前。

### 预取闸门(`perfFlags.js`)

预取是"闲时才做的事":
- 播放器开着 → 全停(它是前台重活)
- 同一时刻只允许**一个**预取在飞,不排队堆积
- 缩略图只预取**下一行**(两行会抢当前可见图片的带宽)

### 播放引擎预热(冷启动后第一次打开,每轮 reload,n=3)

| | 首帧中位 | 引擎 import | 内存 |
|---|---|---|---|
| 预热开 | **1417ms** | 5ms | 19–20MB |
| 预热关 | 1884ms | 271ms | 15–19MB |

首帧 **−467ms(−25%)**。多占的几 MB 是用户迟早要付的钱,只是挪到了空闲时段;
且要求停留 2 秒后才预热 —— 免得为"开机即退出"的人白花内存。

## 四、测过但**没有效果**的改动

- **滚动脱离 React**(焦点移动不再触发两次全量重渲染):对照实验中差异只有
  1–2ms,在噪声里。真机 p95 92ms 的尾巴**不是** React 渲染造成的 ——
  当前假设是图片解码抢主线程,待真机验证。改动保留(方向正确、无副作用),
  但**不作为已验证的收益**。

## 五、真机最终结果(LG C4,2026-08-31,同一时段交替 A/B ×3 轮)

用 `FLAGS` 开关在**同一构建**上交替跑 OFF/ON,消除跨天网络漂移:

| 指标 | 优化前 | 优化后 | 改善 |
|---|---|---|---|
| **翻页 p50** | 387ms | **74ms** | **−81%** |
| **图片 p50** | 1427ms | **462ms** | **−68%** |
| 图片 p95 | 1775ms | **997ms** | −44% |
| **长任务合计** | 1716ms | **864ms** | **−50%** |
| 跟手 p50 | 29.0ms | 27.5ms | −5% |
| 跟手 p95 | 84.3ms | 77.0ms | −9% |
| 内存 | 10MB | 10MB | 持平 |

翻页 4 次**全部命中预取**(优化前 0 次)。

### 中途发现的两个问题(都靠观测抓到)

1. **无节制预取会拖垮机器**:第一版让图片慢一倍、首帧慢 2.3 倍、长任务涨 10 倍。
   → 加预取闸门(播放器开着全停、同时只允许一个在飞、缩略图只预一行)。
2. **预取抢按键路径**:跟手 p50 从 24.5 退到 30.2ms。
   → 预取一律**等焦点停稳 200–250ms** 再做。连续按方向键时零额外工作。

### 观测工具自己的 bug

一个 200 条的大环形数组,被一屏 173 张图片的打点挤爆,翻页记录全丢,报告显示
"无样本"。→ 改成**按指标分桶**(每桶 60 条),互不挤占。
