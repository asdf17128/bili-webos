# 电视长时间加载排查 · 2026-09-06

范围：读取已安装开发包的服务错误环、浏览器历史控制台，并被动观察当前播放 45 秒。没有重载页面或部署应用。

## 已确认

1. 服务错误环有 5 次不同的上游超时：图片域名 i0.hdslb.com 3 次、视频域名 upos-sz-mirrorcos.bilivideo.com 1 次、api.bilibili.com 1 次。图片与视频超时分别记入 req/proxy 两层，不能把 9 条日志算成 9 次故障。图片资源计时记录有 10,033ms、10,104ms 的失败。
2. 一次视频加载记录先出现分片长度不符警告及 Shaka 1001，然后连续 11 次 7000，约 8 秒后才退出重试。当前依赖中的 7000 明确表示 load 被 unload 或另一次 load 中断。PlayerPage 的双层重试没有区分取消与可重试错误，也没有在异步加载流程中持续检查组件存活状态，因此旧播放器可以继续请求 playurl。历史控制台不能单独确定这次中断是用户退出、切换还是其他 load。
3. service.js 的 decompressResponse 只监听 data/end，不处理 error/aborted/close；lunaFetch 没有独立截止时间。用原函数和 Node 流复现：正常响应回调 1 次，响应体接收一半后断开回调 0 次。这是可能造成无限“加载中”的代码路径，尚不能仅凭已有电视日志断定用户每次长等待都经过此路径。

## 当前观测

45 秒内没有加载画面或新的超时；21 个媒体请求均成功且小于 2 秒，播放缓冲持续充足，JS 堆约 51MB。说明故障是间歇性的，这次播放观察没有复现持续卡住。

## 2.0.0 已完成的修复

- 已停止取消或销毁后的播放器重试；普通网络失败最多两次外层尝试，解码类失败保留画质降级。
- API 响应体 error / aborted / 提前 close 都会结束请求；Luna fetch 增加 20 秒截止时间，忽略迟到回调。断流、压缩损坏、取消及超时均有回归测试。
- 浏览器播放器异常回归 9/9 通过，服务响应体测试 8/8 通过。未把这段正常播放观察当作全部网络问题消失的证明；上游 CDN 和 API 的间歇超时仍可能发生。

被动采集工具：`node tools/inspect-tv-loading.mjs 45`。只保存接口 host/path、状态、耗时和播放状态，不保存 Cookie、请求体或签名查询参数；采集结束恢复临时 Luna 计时包装。
